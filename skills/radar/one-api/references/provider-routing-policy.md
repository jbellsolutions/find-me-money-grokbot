# Catalog-driven provider selection

The planner's provider comparison is executable policy in `src/one_api/routing.py`, not a list of vendor suggestions. `orchestrator.plan` infers the operation from source/request or accepts an explicit `capability`, and uses the full dated catalog to find providers for that exact operation. It refreshes up to four shortlisted contracts through saved free catalog reads before ranking.

## Selection algorithm

1. Match the exact capability. An explicit capability selects the phase ahead of incidental keywords: collecting email fields from a public page keeps free/owned extraction first; work-email finding and verification use exact identity/address inputs. A missing address on an explicit verify phase stays a missing input, not an implicit find call. A group profile is not group posts; group posts are not a complete membership export; comments and profiles are different operations. Account/utility/action endpoints are not collection candidates.
2. Match native input requirements. Bind only known URL/query/identity fields. Missing IDs, dataset IDs, conditional identity or account authorization remain gaps. A public task cannot use an own-account operation. A catalog entry is not a credential grant or execution adapter.
3. Compare effectiveness evidence before spending. Use pooled semantic hit statistics when at least 20 decided hit samples exist. Keep delivery success in a separate field: a 99.9% HTTP success rate does not cancel a 60% semantic hit rate. With no semantic evidence, label the option delivery-only or unknown. Mark observations whose last success is over seven days old as stale. Show sample counts, metric basis and an approximate Wilson 95% lower bound based on the reported rounded rate.
4. Use explicit evidence tiers: semantic hits at least 90%; reliable delivery-only at least 95%; mixed semantic hits at least 80%; unknown/stale/weak delivery; semantic hits below 80%. These are transparent policy thresholds, not proven probabilities for the requested task. Requested output fields remain unverified until actual records are checked.
5. Respect billing units. A listed per-call/per-success quote is a planning estimate, not a promised final charge. A per-result price is multiplied by `expected_records` only when its unit and per-count are unambiguous. Credit/character/unsupported units remain unknown; they are never treated as zero. Record the native price note and source/checked date. A route price may be a floor; native final billing and the dispatch cap remain authoritative.
6. Offer four alternatives within operation/access and evidence tiers. `lowest_cost` compares estimated cash first; `fastest` compares measured median time first; `most_reliable` compares the corresponding evidence lower bound; `balanced` minimizes estimated cash plus median seconds × `time_value_usd_per_hour` / 3600. The default $30/hour is a visible configurable planning assumption, not an inferred owner preference. Unknown prices/latencies remain unknown. Alternatives can coincide when one provider dominates.
7. Rank actual enabled options using this comparison. Fixed reviewed ScrapeCreators and AnyAPI social reads can execute under the existing goal/cap ledger. Inventory-only alternatives stay visible with their missing-adapter/input/access reasons. The catalog's preferred provider may differ from the best enabled route; do not hide that gap or silently enable it.
8. Compare owned extraction/free HTTP and existing managed/browser routes against the task. Free static retrieval stays first when it fits. Browser Use Cloud remains preferred for requested rendered JavaScript pages. A custom scraper specification produces owned versioned code; it does not solve a login wall. Optional Jev remains a separately billed typed advisory for the calling agent.
9. Execute the selected saved option once. Check actual fields, attribution, duplicates, cursor/coverage and native costs before continuing or choosing a fallback. A provider observation or successful response is not task completion. Paid uncertainty is reconciled using the original receipt; never substitute another dispatch to recover a lost answer.

## Planner inputs and output

Optional planner fields: `capability`, `preference` (`balanced`, `lowest_cost`, `fastest`, `most_reliable`), `expected_records` (1–100, default 20), `time_value_usd_per_hour` (0–10,000, default 30), and `source_scope` (`public`, default; or `own_account`, which is a request, not an access grant).

`provider_comparison` returns the exact operation, full candidate list, live-versus-snapshot provenance, native inputs/missing fields, access gaps, unit-aware cost estimate, distinct semantic/delivery statistics, four alternatives and the rule used. Enabled social options carry their `provider_evidence` and catalog rank; saved plans do not change after a later price/statistics update. A fresh observation requires a new planning request ID.

## Reviewed social execution scope

Six ScrapeCreators GET reads: Facebook group posts/post comments, TikTok video comments, Instagram post comments, LinkedIn person profile/public post search. Five AnyAPI POST data reads: Facebook group posts, Instagram post comments, TikTok video comments, LinkedIn person profile and public post search. All AnyAPI inputs are body-only and schema-checked; optional proxy query machinery such as jq, custom headers/cookies and arbitrary endpoint IDs remain unavailable. Native method/path/kind/async/eligibility/price contracts are checked before dispatch, and each call uses the existing reservation, upstream idempotency and native billing rules.

The complete provider census remains larger than this reviewed execution scope. Source URLs, provider limits and all operation contracts remain in the per-provider guides and `accounting.*` tools. No new own-account OAuth grant, outreach or unattended campaign runner is implied.
